# Multilanguage support (en, it, fr, de, es) — design

## Goal
The desktop app UI, user-visible backend errors, and chat answer language work in English, Italian, French, German and Spanish. The user picks the language in Settings; default is the OS language, falling back to English.

## Non-goals
- Translating log lines (Python `logger.*`, Rust `supervisor.log`). They stay English for grep-ability and bug reports.
- A separate "answer language" setting. Answers follow the UI language.
- RTL support, pluralisation beyond what i18next provides out of the box, per-document language detection.
- Translating documentation / README.

## Architecture
Frontend owns all translation. Backends stay language-agnostic and emit stable error codes.

### 1. Frontend (`apps/desktop`)
- Deps: `i18next`, `react-i18next`.
- Catalogs: `src/locales/{en,it,fr,de,es}.json`, nested by feature (`chat.*`, `library.*`, `settings.*`, `errors.*`, `common.*`). `en` is the source of truth and the type source (typed keys via module augmentation).
- `src/lib/i18n.ts`: init i18next, bundle all catalogs statically (5 small JSON files, no lazy loading), `fallbackLng: "en"`.
- Language state: `localStorage` key `language` (`"system" | "en" | "it" | "fr" | "de" | "es"`), default `"system"`. `"system"` resolves via `navigator.language` primary subtag, unsupported → `en`. Sets `document.documentElement.lang`.
- Settings: a language `Select` in the general settings panel (options labelled in their own language, plus "System").
- Replace hardcoded strings in all `routes/*` and `features/*` and `components/*` with `t(...)`. Interpolation via `{{var}}`; plurals via i18next `_one/_other`.
- `src/lib/format.ts`: replace `undefined` locale in `Intl.RelativeTimeFormat` with the active language; translate `"never"`, `"—"` stays. `bytes/ms/count` unit symbols stay (SI-style, language-neutral), decimal separators via `Intl.NumberFormat(lang)`.

### 2. Error codes
- Python: introduce `ApiError(status, code, message, **params)` helper in `ragcore/api/errors.py` that raises `HTTPException(status, detail={"code": code, "message": message, "params": params})`. Migrate the ~72 `HTTPException` sites incrementally, starting with those the UI surfaces; un-migrated sites keep string `detail`.
- Rust `proxy.rs`: shell-originated errors (`ragcore unreachable`, `invalid path`, `unsupported method`, `invalid JSON`) become a JSON-encoded error string `{"code": "...", "message": "..."}`; upstream `detail` is passed through untouched.
- `ipc.ts`: `IpcError` gains optional `code` and `params`, parsed from the error payload when it is JSON with a `code`; otherwise `code` is undefined and `message` is the raw text.
- UI: one helper `errorText(err, t)` → `t("errors." + code, params)` if the key exists, else `err.message`. All toast/alert sites go through it.
- Stream frames (`frame.message` in `onFailed`) get the same optional `code`.

### 3. Answer language
- Chat query request body gains `lang` (one of the five codes), sent by `ipc.ts` from the resolved language.
- `ragcore` chat/answer prompt builder (`backend.py`) appends "Answer in <Language>." when `lang` is set and not `en`. The stub answers (`stub/answers.py`) ignore it.
- Missing `lang` → current behaviour (no instruction).
- Regenerate `api-types.ts` via `gen:types`.

### 4. Translations
Written by Claude for it/fr/de/es, in neutral UI style: infinitive/imperative labels ("Aggiungi", "Ajouter", "Hinzufügen", "Añadir"), avoiding tu/vous/du/Sie/tú address where possible. Flag for native review before release.

## Testing
- Vitest: every locale has exactly the key set of `en` (no missing, no extra) and identical `{{placeholders}}` per key.
- Vitest: language resolution (`system` + `it-IT` → `it`; `pt-BR` → `en`; explicit choice wins).
- Vitest: `errorText` — known code → translated, unknown code → raw message, non-JSON error → raw message.
- Vitest: `IpcError` parses JSON error payload.
- pytest: `ApiError` yields `detail` with code/message/params; chat prompt contains language instruction only when `lang` != en.
- Manual: switch each language in Settings, walk every route, trigger an offline-ragcore error.

## Rollout
Single branch, commits per layer: (1) i18n infra + settings picker + `en` catalog extraction, (2) error-code plumbing, (3) answer language, (4) it/fr/de/es catalogs. After changes run `scripts/install-local.sh` (project memory rule). No release.

## Risks
- ~45 files touched; mechanical but large. Mitigated by the catalog-parity test and typed keys.
- Long German strings may overflow tight layouts (sidebar, buttons); check during manual pass.
- Half-migrated backend errors show English until migrated; acceptable, fallback covers it.
